# Base de datos

## Motor

PostgreSQL gestionado en **Supabase**. Las tablas **no se crean desde el backend**:
el esquema se aplica manualmente en el SQL Editor de Supabase.

## Cómo crear las tablas

1. Abrir el proyecto en Supabase → **SQL Editor**.
2. Pegar y ejecutar el contenido de [`database/schema.sql`](../database/schema.sql).
3. En **Project Settings → API Keys** copiar la URL del proyecto y las claves.
4. Configurar las variables de entorno del backend (`backend/.env`):

```env
SUPABASE_URL=https://<proyecto>.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
SUPABASE_SECRET_KEY=sb_secret_...
```

> La clave secreta se usa **solo en el backend** y viaja en cada petición a
> `/rest/v1` como `apikey` + `Authorization: Bearer`. El frontend solo conoce
> la URL de Spring Boot.

## Acceso a los datos

- El backend no abre conexiones JDBC: lee y escribe por la **API REST de
  Supabase** (PostgREST) en `<SUPABASE_URL>/rest/v1/<tabla>`.
- Los nombres de columna del JSON son **snake_case** (`id_campana`,
  `fecha_riego`, `cantidad_m3`…), idénticos al esquema SQL.
- Las claves primarias se generan en la base de datos; el backend no envía `id`.
- Los nombres mostrados (`nombreAgricultor`, `nombreCampana`, …) se resuelven con
  peticiones de apoyo (`in (…)`) porque **no son columnas**.

## Restricciones de implementación

- No hay Hibernate ni Flyway: `spring-boot-starter-data-jpa`, `postgresql` y
  `flyway-*` fueron retirados de `pom.xml`. La aplicación no altera ni valida el
  esquema; solo lo consume.
- Las claves primarias **deben ser de identidad**
  (`BIGINT GENERATED BY DEFAULT AS IDENTITY`), porque PostgREST las devuelve al
  insertar (`Prefer: return=representation`).
- **RLS**: activar Row Level Security en las 8 tablas. Con la clave secreta el
  backend opera con permiso total; si se deja solo la publishable, las
  escrituras responden `409` con el error de PostgREST.
- Cada operación es una petición HTTP independiente: **no hay transacciones
  multi-tabla**. Las reglas de negocio se comprueban antes de escribir y los
  borrados se protegen con `409 Conflict`.

## Modelo de datos

Las ocho tablas y sus claves foráneas siguen exactamente `project.md`:

| Tabla | PK | FK |
|---|---|---|
| `agricultor` | `id_agricultor` | — |
| `parcela` | `id_parcela` | `id_agricultor` → `agricultor` |
| `cultivo` | `id_cultivo` | — |
| `campana` | `id_campana` | `id_parcela` → `parcela`, `id_cultivo` → `cultivo` |
| `riego` | `id_riego` | `id_campana` → `campana` |
| `gasto` | `id_gasto` | `id_campana` → `campana` |
| `cosecha` | `id_cosecha` | `id_campana` → `campana` |
| `venta` | `id_venta` | `id_cosecha` → `cosecha` |

### Tipos (decisión documentada)

El diagrama original no estaba disponible en el repositorio; se confirmó con el
usuario el uso de tipos estándar:

- Identificadores: `BIGINT` identidad.
- Texto: `VARCHAR(n)` con `NOT NULL` donde aplica.
- Fechas: `DATE`.
- Áreas/cantidades/montos: `NUMERIC` con `CHECK (valor >= 0)`
  (y `area_hectareas > 0`).
- `campana.fecha_fin` es **anulable** (campaña en curso) y
  `CHECK (fecha_fin >= fecha_inicio)`.
- `cultivo.nombre` **no** tiene `UNIQUE` (no está en el modelo original).

## Reglas de integridad en la aplicación

Además de las restricciones SQL, la API valida en tiempo de ejecución:

- Existencia de las entidades referenciadas antes de insertar.
- `fecha_fin >= fecha_inicio`.
- La suma de `venta.cantidad_kg` por `cosecha` no supera `cosecha.cantidad_kg`.
- **Sin borrados en cascada**: si existen registros dependientes, el `DELETE`
  devuelve `409 Conflict` para preservar el histórico.
